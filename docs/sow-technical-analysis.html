Executive Summary

TraderPro is a production-ready, full-stack crypto trading platform built over approximately 6 months of active development. The platform integrates 13 external data providers, 108 REST API endpoints, 19 database tables across two SQLite instances, and 40+ user-facing features spanning technical analysis, on-chain data, AI reasoning, backtesting, portfolio management, and localised market data for Pakistan and emerging markets.

This document serves as (1) the Statement of Work for Phase 2 development, (2) a comprehensive technical analysis of the current system, and (3) a complete security audit report with remediation status.

🏗 System Architecture

Architecture Overview

TraderPro is a monolithic Node.js/Express application with two satellite Python microservices. The frontend is a multi-module vanilla JavaScript SPA served as static files. A background cron loop handles server-side alert evaluation every 60 seconds.

Data Flow

All authenticated client requests include a X-CSRF-Token header via AuthUtils.apiFetch(). The CSRF middleware validates this against the session-bound token for all non-GET, non-exempt routes. API responses are cached in an in-memory TTL store to reduce external API calls and respect free-tier rate limits.

🔐 Security Posture

Implemented Controls

  • ✓
    bcrypt password hashing — 12 salt rounds, constant-time comparison (bcryptjs)
  • ✓
    CSRF protection — Double-submit pattern: X-CSRF-Token header validated against session.csrfToken for all non-GET mutations
  • ✓
    Session fixation prevention — session.regenerate() called on login (both full and 2FA-pending paths)
  • ✓
    TOTP 2FA — speakeasy RFC 6238, ±1 window tolerance, QR code provisioning, disable requires password
  • ✓
    Content Security Policy — Helmet CSP with allowlisted CDN origins, no unsafe-eval, frame-ancestors: none
  • ✓
    XSS prevention — esc() helper applied to all innerHTML in all 6 client modules; safeMd() for LLM text rendering
  • ✓
    SQL injection prevention — Parameterized queries throughout (better-sqlite3 .prepare().run())
  • ✓
    Rate limiting — Auth: 15/15min; General API: 200/15min; Slack proxy: 10/10min; Admin mutations: 30/1min
  • ✓
    SSRF prevention — Slack webhook URL validated with new URL() + exact hostname check (hooks.slack.com only)
  • ✓
    Input validation — validSymbol() regex guard on all symbol params; safeInt() on all numeric query params
  • ✓
    Email enumeration prevention — /api/auth/forgot-password always returns 200 regardless of email existence
  • ✓
    API key masking — /api/user/keys returns only suffix + _set flag, never raw values
  • ✓
    Production error suppression — Generic errors in IS_PROD=true; detailed errors in dev only
  • ✓
    Startup guards — Server refuses to start without SESSION_SECRET; refuses in production without ALLOWED_ORIGINS
  • ✓
    Admin route protection — requireAdmin middleware validates role + non-suspended status on every request
  • ✓
    Admin ID validation — parseAdminUserId() rejects NaN, zero, negative IDs with 400 error
  • ✓
    Alert cron timeout — AbortSignal.timeout(8000) on Binance fetch in alert cron
  • ✓
    CSV formula injection — Admin waitlist export strips leading =+@- characters (Excel formula injection prevention)
  • ~
    API key storage — Stored in DB, masked on retrieval; not yet encrypted at rest (Phase 2)
  • ~
    Password reset tokens — Stored as plain hex in DB; not yet hashed before storage (Phase 2)
  • ~
    Per-user rate limiting — IP-based only; no per-authenticated-user limits (Phase 2)
  • ○
    Microservice auth — Node↔Python communication unprotected (localhost assumption) — Phase 2
  • ○
    DB encryption — SQLite files unencrypted at rest — Phase 3 (SQLCipher)

🛠 Remediation Log

Session Fixation Fix (S-12)

Added req.session.regenerate() on both the full login path and the 2FA pending path. The session ID is cryptographically replaced after successful password verification, preventing fixation attacks where an attacker pre-plants a session ID.

// Before 2FA pending state
await new Promise((resolve, reject) =>
  req.session.regenerate(err => err ? reject(err) : resolve()));
req.session.pendingTotpUserId = result.user.id;

SSRF Fix — Slack Proxy (S-04)

Replaced startsWith('https://hooks.slack.com/') with full URL parsing. The parsed hostname is checked exactly against 'hooks.slack.com', preventing path-based bypass and protocol confusion attacks.

let parsedUrl;
try { parsedUrl = new URL(webhook); } catch { /* invalid */ }
if (!parsedUrl || parsedUrl.protocol !== 'https:'
    || parsedUrl.hostname !== 'hooks.slack.com') {
  return res.status(400).json({ error: 'Invalid webhook URL' });
}

XSS Fix — LLM Engine (S-01, S-02)

Introduced safeMd() which escapes HTML before applying markdown transforms, ensuring injected <script> tags in LLM API responses cannot execute. Applied esc() to all agent data fields rendered via innerHTML.

function safeMd(s) {
  return esc(s)  // escape FIRST
    .replace(/\*\*(.*?)\*\*/g, '<strong>$1</strong>')
    .replace(/\n\n/g, '</p><p>')
    .replace(/\n/g, '<br/>');
}

safeInt() Helper — NaN Prevention (S-05, S-17)

Added a global helper that guards all integer query parameter parsing. Returns the fallback value if parsing yields NaN, and optionally caps at a maximum to prevent resource exhaustion via large limit values.

function safeInt(val, fallback, max) {
  const n = parseInt(val, 10);
  const result = Number.isFinite(n) ? n : fallback;
  return max !== undefined ? Math.min(result, max) : result;
}
